# PyProlog 高速化・最適化 改善提案書 (Rev.2)

## 概要

本提案書は、Pythonで実装されたPrologインタプリタ `PyProlog` のパフォーマンスを最大化するための改修計画です。
既存のロジックを維持しつつ、ボトルネックとなる「全探索」「環境コピー」「オブジェクト生成」の3点を、Rust製ライブラリ（`rpds`, `msgspec`）の導入とアルゴリズムの改善によって解消します。

## 1. アルゴリズムの改善：述語インデックスの導入（最重要）

**課題:**
現在の `solve_goal` は、ゴールを解決するたびにデータベース内の**全ルールを先頭から線形探索（計算量 O(N)）** しています。ルール数 N が増加すると処理速度が著しく低下します。

**解決策:**
述語名と引数数（アリティ）をキーとするハッシュマップ（インデックス）を導入し、探索候補の取得を **計算量 O(1)（平均）** に短縮します。

**実装仕様 (`pyprolog/runtime/logic_interpreter.py`):**

1. **データ構造:**
* `self.rules_index`: `Dict[Tuple[str, int], List[Union[Rule, Fact]]]`
* キー: `(functor_name, arity)`
* 値: ルール/事実のリスト（定義順序を保持）


2. **インデックス更新戦略（動的述語対応）:**
静的なロード時だけでなく、動的な変更 (`assert`, `retract`) に追従する必要があります。
* **初期化時:** 全ルールをスキャンしてインデックスを構築。
* **`assertz` (末尾追加):** 対象キーのリストの**末尾**にルールを追加し、`self.rules` にも同じ順序で末尾追加する。
* **`asserta` (先頭追加):** 対象キーのリストの**先頭**にルールを追加し、`self.rules` にも同じ順序で先頭追加する。
* **`retract` (削除):** 対象キーのリストから単一化可能な最初のルールを削除し、`self.rules` からも同一要素を削除して整合性を保つ。
* **ロールバック:** `assert`/`retract` 自体がバックトラック可能な操作ではない（Prologの標準仕様として論理的副作用は残る）ため、複雑なロールバック機構は不要ですが、インデックスと `self.rules` の整合性は常に保つ必要があります。



```python
    def _build_index(self):
        self.rules_index = {}
        for rule in self.rules:
            self._add_to_index(rule)

    def _add_to_index(self, rule, position="last"):
        key = (rule.head.functor.name, len(rule.head.args))
        if key not in self.rules_index:
            self.rules_index[key] = []
        
        if position == "first":
            self.rules_index[key].insert(0, rule)
        else:
            self.rules_index[key].append(rule)

```

## 2. 環境管理の高速化：Rust製 `rpds` の導入（効果：大）

**課題:**
探索（バックトラック）や `unify` の試行において、標準の `dict.copy()` が多用されています。これは要素数 N に対して **計算量 O(N)** のコストがかかり、再帰深度に伴い指数関数的に負荷が増大します。

**解決策:**
Rust製ライブラリ **`rpds` (Rust Python Data Structures)** の `HashTrieMap` を導入します。
これにより、環境の論理コピーおよび更新（insert）操作は、データ量に関わらず **計算量 O(1) (償却/Amortized)** となります。

**ミュータブル/イミュータブル方針の定義:**
`rpds` のマップ自体はイミュータブル（不変）ですが、`BindingEnvironment` クラスは Python のオブジェクトとしてミュータブル（可変）な振る舞いを維持し、既存コードとの互換性を保ちます。

* **内部ストレージ (`self.bindings`):** `rpds.HashTrieMap` (イミュータブル)。変更時は新しいインスタンスに差し替える。
* **ラッパークラス (`BindingEnvironment`):** ミュータブル。`bind` メソッドは `self.bindings` の参照先を更新する。

**実装仕様 (`pyprolog/core/binding_environment.py`):**

```python
import rpds

class BindingEnvironment:
    def __init__(self, parent=None, bindings=None):
        # bindings が None なら空の HashTrieMap を作成
        self.bindings = bindings if bindings is not None else rpds.HashTrieMap()
        self.parent = parent

    def bind(self, var_name: str, value):
        # 【方針】rpdsは不変なので、insertした結果（新しいMap）を self.bindings に再代入する
        # これにより、この環境オブジェクトを持っている側からは「値が書き換わった」ように見える
        self.bindings = self.bindings.insert(var_name, value)

    def copy(self):
        # 【高速化】コピーは内部Mapの参照を渡すだけ。O(1)。
        # 親子関係や探索位置の保存のために新しい BindingEnvironment ラッパーは作成する。
        return BindingEnvironment(self.parent, bindings=self.bindings)

```

## 3. データ型定義の最適化：Rust製 `msgspec` の導入（効果：中〜大）

**課題:**
`Term` 等のオブジェクト生成コストとメモリ消費量削減のため `msgspec.Struct` を導入しますが、これはデフォルトでイミュータブルかつ厳格です。既存の「後から属性を変更する処理」や「I/O出力」との互換性が課題となります。

**解決策:**
`msgspec.Struct` をベースにしつつ、既存コードの動作要件に合わせて設定を調整し、互換性を担保します。

**確認・設定項目:**

1. **属性変更の許可 (`frozen=False`):**
`LogicInterpreter` 内で、コピー後の `Term` の `args` を差し替える処理 (`instantiate_term` 等) が存在します。
* **対応:** `msgspec.Struct` 定義時に、必要に応じてミュータブルな設計にするか、あるいは「常に新しいオブジェクトを作る」設計に寄せます。当面は移行コストを下げるため、リスト等のミュータブルなフィールドを許容します。


2. **I/O互換性 (`repr`/`str`):**
`msgspec.Struct` のデフォルトの `repr` は `Atom(name='a')` のような形式ですが、Prologとしては `a` と表示したい場合があります。
* **対応:** 既存の `__repr__` メソッドを必ず再定義（または維持）し、Prolog形式の出力が崩れないことを単体テストで保証します。


3. **シリアライズ互換:**
既存のシリアライズ/デバッグ出力の期待値が崩れないことをテストで担保します。
* 既存テストに「出力の文字列一致」や「JSONの比較」がある場合は**その期待値が変わらない**ことを確認。
* 追加で必要なら、`types.py` の `__repr__` と `msgspec` 変換の回帰テストを用意する。

**実装仕様 (`pyprolog/core/types.py`):**

```python
import msgspec
from typing import List, Any

# array_like=True: 位置引数での初期化などをリストのように扱える（必要に応じて）
# omit_defaults=True: デフォルト値を持つフィールドの省略を許可
class BaseTerm(msgspec.Struct, array_like=True):
    pass

class Term(BaseTerm):
    functor: Any
    args: List[Any]  # Pythonのlistを使用することで、argsの内容変更は許可される

    # 既存の __repr__ を維持し、I/O互換性を確保
    def __repr__(self):
        if not self.args:
            return repr(self.functor)
        return f"{repr(self.functor)}({', '.join(map(repr, self.args))})"

```

## 4. 実行時オーバーヘッドの削減と例外方針

**課題:**
`unify` メソッド内の広範な `try-except Exception` は、単一化の失敗だけでなく、バグ（AttributeError等）も隠蔽してしまい、かつ実行速度を低下させています。

**解決策:**
不要な例外処理を削除します。ただし、挙動の変化に注意が必要です。

**変更方針:**

1. **例外処理の削除:**
`BindingEnvironment.bind` (および `rpds.insert`) は、メモリ不足等の致命的状況を除き、通常の使用法で例外をスローしません。したがって `try-except` は不要です。
2. **影響範囲と例外ポリシー:**
* **変更前:** `term1.name` が存在しないオブジェクトが渡された場合など、本来クラッシュすべきバグが `return False` (単一化失敗) として扱われていた可能性があります。
* **変更後:** バグがある場合は `AttributeError` 等が**呼び出し元に伝播（クラッシュ）**します。
* **方針:** これは「正しい挙動」への修正です。開発段階でバグを検知できるようにするため、例外は握りつぶさず、単一化の論理的失敗（型不一致など）のみを `False` で返すように実装します。



```python
    def unify(self, term1, term2, env):
        # ... (前略)
        # 変数束縛のケース: try-except を削除
        if isinstance(term1, Variable):
            env.bind(term1.name, term2)
            return True, env
        # ... (後略)

```

## 5. 追加の高速化策（検討候補）

**目的:** 既存4項目で届かない場合の次の一手として、実装コストと効果のバランスで候補を提示します。

1. **多引数インデックス（2nd/3rd arg indexing）:**
第1引数以外でも高選択度がある場合に、キーを拡張して候補集合をさらに絞り込みます。  
例: `(functor, arity, arg1)` に加え `(functor, arity, arg2)` を併用し、最小候補のインデックスを選択。

2. **タブリング（メモ化）:**
再帰や重複計算が多い述語に対して、ゴールと結果をキャッシュします。  
効果は大きい一方でメモリ消費増と、動的述語更新時の無効化戦略が必要です。

3. **アトムのインターン化（Atom Table）:**
同一文字列の `Atom` を共有化し、比較を参照等価に寄せます。  
字句解析時にテーブルへ登録し、`Atom` 作成コストを抑制します。

4. **トレイル管理の最適化:**
バックトラック復元用の「変更ログ（trail）」を導入し、環境全体のコピーを避けます。  
実装は難度高だが、`BindingEnvironment` の改修と相性が良いです。

5. **ホットパスの関数内最適化:**
`unify` と `solve_goal` の分岐回数削減（早期リターン/局所変数化）や、頻出の型判定の並べ替えでCPU分岐ミスを減らします。

1. **Step 1 (ロジック):** `LogicInterpreter` への述語インデックス導入（更新系ロジック含む）。
2. **Step 2 (環境):** `BindingEnvironment` への `rpds` 導入（`bind` の挙動変更なし）。
3. **Step 3 (オーバーヘッド):** `unify` の `try-except` 削除とロギングガード追加。
4. **Step 4 (データ型):** `types.py` への `msgspec` 導入（`repr` 互換性テスト必須）。
