# PyProlog 高速化・最適化 改善提案書

## 概要

本提案書は、Pythonで実装されたPrologインタプリタ `PyProlog` のパフォーマンスを最大化するための改修計画です。
Pythonの柔軟性を維持しつつ、ボトルネックとなる「探索」「環境コピー」「オブジェクト生成」の3点を、Rust製ライブラリ（`rpds`, `msgspec`）の導入とアルゴリズムの改善によって解消します。

## 1. アルゴリズムの改善：述語インデックスの導入（最重要）

**課題:**
現在の `solve_goal` は、ゴールを解決するたびにデータベース内の**全ルールを先頭から線形探索 ()** しています。ルール数が増加すると処理速度が著しく低下する最大の要因です。

1. **インデックス構築:** `LogicInterpreter` の初期化時にインデックスを作成します。

## 2. 環境管理の高速化：Rust製 `rpds` の導入（効果：大）

**課題:**
Prologのバックトラック（探索）では、変数の束縛状態（環境）を保存・復元するために頻繁に `env.copy()` が実行されます。Python標準の `dict.copy()` は  のコストがかかり、再帰が深くなると致命的な遅延となります。

**解決策:**
Rustで実装された永続データ構造ライブラリ **`rpds` (Rust Python Data Structures)** を導入します。これにより、環境のコピー操作が論理的な参照のみとなり、**データ量に関わらず ** で完了します。

**実装方針 (`pyprolog/core/binding_environment.py`):**

* **ライブラリ:** `pip install rpds-py`
* **データ構造:** `dict` の代わりに `rpds.HashTrieMap` を使用。

```python
import rpds

class BindingEnvironment:
    def __init__(self, parent=None, bindings=None):
        # 初期化は空のHashTrieMap、または引き継いだMap
        self.bindings = bindings if bindings is not None else rpds.HashTrieMap()
        self.parent = parent

    def bind(self, var_name, value):
        # 永続データ構造なので、insertすると新しいMapが返る（元のMapは不変）
        self.bindings = self.bindings.insert(var_name, value)

    def copy(self):
        # 【最重要】コピーは O(1)。単に現在の Map を渡すだけ。
        return BindingEnvironment(self.parent, bindings=self.bindings)

```

## 3. データ型定義の最適化：Rust製 `msgspec` の導入（効果：中〜大）

**課題:**
`Term`, `Atom`, `Variable` などのオブジェクトが大量に生成されます。Python標準のクラスや `dataclass` はメモリオーバーヘッドが大きく、生成コストも無視できません。

**解決策:**
Rust製の高速シリアライザ/バリデータライブラリ **`msgspec`** の `Struct` 機能を利用します。これにより、メモリ使用量を大幅に削減（C言語の構造体に近いレイアウト）し、インスタンス生成を高速化します。

**実装方針 (`pyprolog/core/types.py`):**

* **ライブラリ:** `pip install msgspec`
* **継承元変更:** `BaseTerm` を `msgspec.Struct` 継承に変更。

```python
import msgspec
from typing import List, Any

# msgspec.Struct を継承することで、スロット化以上のメモリ効率と速度を実現
class BaseTerm(msgspec.Struct):
    pass

class Atom(BaseTerm):
    name: str

class Term(BaseTerm):
    functor: Atom
    # Pythonのリストはそのまま保持可能（mutableが必要な場面でも対応可）
    args: List[Any]

```

※ `msgspec` の導入が依存関係等で難しい場合の代替案として、Python標準の `__slots__ = True` を `dataclass` に付与するだけでも20-30%のメモリ改善が見込めます。

## 4. 実行時オーバーヘッドの削減（効果：中）

**課題:**
頻繁に呼び出されるメソッド内のロギング（`logger.debug(f"...")`）や、正常系での例外処理（`try-except`）が、CPUサイクルを無駄に消費しています。

**解決策:**

1. **ロギングのガード:**
`LogicInterpreter` や `unify` などのホットパスにおいて、ログ出力前にレベルチェックを行います。f-stringによる文字列生成コストを回避します。
```python
if logger.isEnabledFor(logging.DEBUG):
    logger.debug(f"Unifying {term1} with {term2}...")

```


2. **`unify` の例外処理削除:**
`BindingEnvironment.bind` は単純な代入操作であるため、`unify` メソッド内の `try-except` ブロックは冗長です。これを削除し、直接実行するようにします。

## 推奨される実装ステップ

リスクを抑えつつ最大の効果を得るため、以下の順序での適用を推奨します。

1. **Step 1 (ロジック):** `LogicInterpreter` への述語インデックス導入。
* *理由:* ライブラリ追加が不要で、計算量オーダーが変わるため最も効果が体感しやすい。


2. **Step 2 (環境):** `BindingEnvironment` への `rpds` 導入。
* *理由:* 修正範囲が特定のファイルに限定され、かつバックトラック性能への寄与が極めて大きい。


3. **Step 3 (オーバーヘッド):** ロギングガードの追加と `try-except` の整理。
* *理由:* 安全かつ地道な高速化。


4. **Step 4 (データ型):** `types.py` への `msgspec` (または `__slots__`) 導入。
* *理由:* プログラム全体に影響するため、最後に適用し、十分な回帰テストを行うべきであるため。
