# 0. 最終ゴール（到達定義）

## G1: Prolog意味論の土台（互換性最優先）

* **述語の存在**と**節の有無**が分離されている

  * 動的更新後でも `p(_)` が **fail** になるだけで **existence_error にならない**（少なくとも “動的に作られた述語” は存在し続ける）
* `asserta/1, assertz/1, retract/1` が

  * ルールDB（節集合）
  * インデクス
  * 候補キャッシュ/dirtyフラグ
    を **一貫更新**する
* `,` 最適化後も **解の順序**が不変
* ベンチ（light/medium/heavy）を回しても **意味論破壊ゼロ**

## G2: 性能ゴール（現状の延長で安全に積む）

* light/medium の改善が crypt/queens/tak の heavy に素直に波及
* ホットパス（execute/unify/deref/math）で **固定費削減**が確認できる（プロファイルで裏取り）

# 1. 中間地点（マイルストーン）と到達条件

## M0: 観測とガードレールの固定

**到達条件**

* ガードレール（動的更新/連言順序/動的削除）が安定稼働
* “この変更で意味論が壊れた”を即検知できる

**必要項目**

* ガードレールを「処理系の設計仕様」に合わせて確定
* ベンチは light/medium/heavy 分離維持

**調査項目（Codexへ）**

* どの述語が「動的に作られた」とみなされるべきか（設計方針の明文化）

---

## M1: 動的更新の意味論を完成（今ここが本丸）

**到達条件**

* `assertz(p(1)).` 後に `p(X).` が見える
* `retract` で全部消しても `p(_)` は **existence_error ではなく fail**
* Phase2のインデクスを入れても **幽霊節が出ない** / **候補が腐らない**

**必要項目**

* 「述語が存在する」メタデータの導入（= predicate registry）
* `asserta/assertz/retract` が

  1. 節を追加/削除
  2. predicate registry を更新
  3. rules_by_pred と indexes を dirty にする
     を必ずやる

**調査項目（Codexへ・最優先）**

* `existence_error` が出る判定ロジックの根拠（`rules_by_pred` のみで判定してないか）
* builtins の assertz/retract がどの層を更新してるか（Runtime / LogicInterpreter / インデクス）
* `_refresh_index_if_needed()` の dirty 条件と更新内容

---

## M2: インデクシング（Phase2）を“動的更新対応”まで仕上げる

**到達条件**

* asserta/assertz/retract 後に arg0 インデクスが即時正しい
* fallback（arg0が複合項/リスト/変数/未対応型）でも探索が正しい
* “順序保持（cut含む）”のテストが通る

**必要項目**

* インデクス構造の更新API（add/remove）
* 候補取得（get_candidate_clauses）とインデクスの整合性契約
* キャッシュがあるなら「世代（generation）」で破棄可能にする

**調査項目（Codexへ）**

* 二次インデクスキーの型対応範囲（Atom/Number/String…）
* 削除時のインデクス更新漏れが起こり得る経路（copy/clone含む）

---

## M3: Phase3.2（unify内deref重複削減）を安全に積む

**到達条件**

* ガードレール全通過
* light/medium のプロファイルで dereference/unify の割合が改善
* crypt での「終わらない」が改善方向に動く

**必要項目**

* unify stack ループ内の deref 呼び出し回数の削減（既に方針あり）
* occurs_check の条件分岐を壊さない
* 共有/破壊的更新を避ける（意味論保持）

**調査項目（Codexへ）**

* deref の呼び出しポイント一覧と “同一変数の多重deref” 発生箇所
* bind のコスト要因（環境コピーや trail の設計）

---

## M4: 重ベンチ（crypt）完走のための“汎用改善”を積む

**到達条件**

* crypt が制限時間内で完走（CIではなく手動/夜間でもOK）
* プロファイルで「探索量×固定費」が固定費側で改善している

**必要項目**

* math/evaluate の固定費削減（評価の局所最適化）
* execute/solve_goal のループ内 allocations 削減
* 必要なら clause selection の追加改善（ただし意味論不変）

**調査項目（Codexへ）**

* execute/solve_goal の hot allocation 源（Term生成、env copy、list構築）
* builtins での不要ログ/変換/再パース

# 2. “まず全部調べる”ための調査リスト（Codexタスク化）

ここから先は **実装に入らず**、全部「調査→メモ化」してから次へ。
Codexに投げる単位を揃えてある。

## 調査パケットA：existence_error の仕様と現在挙動

**目的**：`p/1` が空になると existence_error になる原因を特定（ガードレール失敗の根） 
**Codexプロンプト**

* 「`existence_error(procedure, p/1)` を投げる条件をコード上で列挙し、どのデータ構造を根拠にしているか（rules_by_pred / registry / builtins表）を示して。`assertz`→`retract`→`p(_)` の再現経路で、どのタイミングで “p/1 が存在しない扱い” になるか追跡して。」

**成果物**

* 判定ロジックのフローチャート
* “述語の存在”の現在の定義（＝暗黙に rules_by_pred の存在？）

---

## 調査パケットB：asserta/assertz/retract の更新責務

**目的**：動的更新がどの層を更新してる/してないを整理
**Codexプロンプト**

* 「builtins の asserta/assertz/retract の実装を読み、更新している対象を一覧化して（例：Runtime.rules, LogicInterpreter.rules_by_pred, clause indexes, dirty flags）。更新していないが更新すべき対象も列挙して。」

**成果物**

* “更新責務マトリクス（builtin × 構造体）”
* 不整合が起こる最短パス（今回の失敗と一致させる）

---

## 調査パケットC：インデクス更新モデル（Phase2と整合）

**目的**：静的ビルド前提のインデクスになってないか点検
**Codexプロンプト**

* 「Phase2の index 構造（primary/secondary）と `_refresh_index_if_needed` の実体を確認し、動的変更でどこを更新すべきか（incremental update か full rebuild か）設計案を出して。順序保持と cut の要件を壊さない条件も書いて。」

**成果物**

* 更新戦略（incremental vs rebuild）と採用理由
* dirty 世代管理の案

---

## 調査パケットD：ガードレール仕様の確定（最終像から逆算）

**目的**：テストを“仕様書”として固定する
**Codexプロンプト**

* 「この処理系の ‘動的に作られた述語’ の存在条件を仕様化して。`assertz` で初めて現れた述語は、節が0になっても存在扱いにするか？ `p(_)` は fail か existence_error か？ 既存実装と互換性・実用性から結論を出して。採用仕様に対応するガードレールも提案して。」

**成果物**

* “述語存在仕様” 1枚
* ガードレール確定版（テストコード）

# 3. この資料の使い方（進め方のルール）

* **実装はしない**（調査だけ）
* 上の A〜D を Codex に投げて、成果物が揃ったら

  * 仕様確定（D）
  * 更新責務の穴埋め（B）
  * existence_error の根治（A）
  * インデクス更新方針（C）
    の順に“設計→実装”へ進む

# key takeaways

* いまの詰まりは「最適化」じゃなく **“動的更新の意味論（述語の存在）”の未確定**が原因 
* ゴール→中間地点→必要項目→調査項目 を固定して、場当たりを止める
* Codex に投げる調査パケット（A〜D）を先に全部消化してから次へ進む
