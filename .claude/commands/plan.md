# 計画コマンド

このコマンドは**planner**エージェントを呼び出して、コードを書く前に包括的な実装計画を作成します。

## このコマンドが行うこと

1. **要件の再確認** - 何を構築する必要があるかを明確化
2. **リスクの特定** - 潜在的な問題とブロッカーを表面化
3. **段階計画の作成** - 実装をフェーズに分解
4. **確認を待つ** - 進行前にユーザーの承認を必須とする

## 使用タイミング

以下の場合に`/plan`を使用：
- 新機能の開始
- 重要なアーキテクチャ変更の実施
- 複雑なリファクタリングの作業
- 複数のファイル/コンポーネントが影響を受ける場合
- 要件が不明確または曖昧な場合

## 動作方法

plannerエージェントは以下を行います：

1. **リクエストを分析**し、要件を明確な用語で再確認
2. **フェーズに分解**し、具体的で実行可能なステップを作成
3. **依存関係を特定**コンポーネント間の関係を明確化
4. **リスクを評価**し、潜在的なブロッカーを特定
5. **複雑度を推定**（高/中/低）
6. **計画を提示**し、明示的な確認を待つ

## 使用例

```
ユーザー：/plan マーケットが解決された時のリアルタイム通知を追加する必要がある

エージェント（planner）：
# 実装計画：マーケット解決リアルタイム通知

## 要件の再確認
- ユーザーがウォッチしているマーケットが解決された時に通知を送信
- 複数の通知チャネルをサポート（アプリ内、メール、webhook）
- 通知が確実に配信される
- マーケット結果とユーザーのポジション結果を含める

## 実装フェーズ

### フェーズ1：データベーススキーマ
- 通知テーブルを追加：id、user_id、market_id、type、status、created_at列
- ユーザー通知設定テーブルを追加（チャネル設定用）
- パフォーマンス用にuser_idとmarket_idにインデックスを作成
- Alembicマイグレーション作成

### フェーズ2：通知サービス
- app/services/notifications.pyに通知サービスを作成
- Celery/Redisを使用して通知キューを実装
- 失敗配信用の再試行ロジックを追加
- Jinja2で通知テンプレートを作成

### フェーズ3：統合ポイント
- マーケット解決ロジックにフック（ステータスが「解決済み」に変更時）
- マーケットにポジションを持つすべてのユーザーをクエリ
- 各ユーザーの通知をキューに追加

### フェーズ4：フロントエンドコンポーネント
- ヘッダーに通知ベルコンポーネントを作成（Jinja2 + htmx）
- 通知リストモーダルを追加
- htmxポーリングまたはWebSocket経由でリアルタイム更新を実装
- 通知設定ページを追加

## 依存関係
- Redis（キュー用）
- Celery（バックグラウンドタスク）
- メールサービス（SendGrid/Resend）

## リスク
- 高：メール配信性（SPF/DKIM必須）
- 中：マーケットあたり1000+ユーザーでのパフォーマンス
- 中：マーケットが頻繁に解決される場合の通知スパム
- 低：リアルタイム更新のオーバーヘッド

## 推定複雑度：中
- バックエンド：4-6時間
- フロントエンド：3-4時間
- テスト：2-3時間
- 合計：9-13時間

**確認待ち**：この計画で進めますか？（yes/no/modify）
```

## 重要な注意事項

**重要**：plannerエージェントは「yes」または「proceed」または類似の肯定的な応答で明示的に計画を確認するまで、**コードを書きません**。

変更が必要な場合は、以下で応答：
- 「modify: [あなたの変更]」
- 「different approach: [代替案]」
- 「skip phase 2 and do phase 3 first」

## 他のコマンドとの統合

計画後：
- `/tdd`を使用してテスト駆動開発で実装
- ビルドエラーが発生した場合は`/build-fix`を使用
- 完了した実装をレビューするために`/code-review`を使用
